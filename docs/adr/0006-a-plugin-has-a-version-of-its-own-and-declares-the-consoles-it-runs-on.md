# ADR-0006: A plugin has a version of its own and declares the consoles it runs on

- Status: Accepted; who publishes the first version, in point 4, is superseded by [ADR-0007](0007-a-plugin-is-named-on-the-registry-by-hand-and-its-first-version-is-the-workflows.md)
- Date: 2026-11-06
- Supersedes [ADR-0005](0005-a-plugin-is-versioned-on-the-consoles-line-with-a-patch-of-its-own.md). Point 3 of [ADR-0002](0002-one-package-per-plugin-published-to-the-registry-under-one-scope-and-versioned-on-its-own.md) stands again as written; point 2 of [ADR-0003](0003-every-plugin-is-built-against-one-version-of-the-console-and-they-move-together.md) is amended as point 3 below says. The rule is held by `scripts/check-versions.mjs`; what a changeset says is in [.changeset/README.md](../../.changeset/README.md), and the procedure in [guide/releasing.md](../guide/releasing.md).

## Context

ADR-0005 put a published plugin's major and minor on the console's line, so that the number said which console a plugin goes with. Two things weigh against it. The plugins of this repository will not be the only ones: a plugin written elsewhere has a version of its own and reasons of its own to bump it, and a reference repository that follows a rule nobody else can follow is a poor reference. And the one thing the line rule bought, that whoever installs a plugin reads off its number the console it goes with, is bought better by a declaration the console reads and checks. The manifest already names the plugins a plugin needs with `requires`, by a semver range of their version; a range of the console's version in the same shape says exactly which consoles a plugin runs on, with the patch floor the line rule could not express. That field is proposed to the console, where the contract is decided ([ADR-0001](0001-this-repository-holds-the-reference-plugins-and-proposes-a-shape-for-a-repository-of-several.md)), and adopted here by version; until then the README and the changelog entry say it in words, as they did.

## Decision

1. **Each plugin is versioned on its own, under semver, from 0.1.0.** The version says what changed in the plugin, nothing of the console: `patch` for a fix and for an addition that changes nothing that exists; `minor` for something new that changes what exists and, while the major is 0, for a breaking change, which is a command or its arguments removed or renamed, a query's answer changed, a role, a setting or a capability asked anew, or the console it needs moved; `major` only when a plugin is declared stable, which waits for the console's 1.0. A plugin that did not change is not re-released, and each has a changelog of its own.
2. **A plugin declares the consoles it runs on.** In the manifest, as `console`, a semver range of the console's version in the shape `requires` has (`">=0.4.3 <0.6"`), once the console reads the field; the console then refuses to run a plugin outside it, says why, and shows the range. Until then, and beside it afterwards, the plugin's README names the console it is built for, and a changelog entry says "built for console 0.4.3 or later" where a release raises the floor. The range moves in the change that moves the catalog, and is narrowed when a release needs a later console; either is a `minor` while the major is 0, since a deployment on a console left out cannot take the release.
3. **One console, the catalog's, inside every range.** `@skillcdn/console` stays at one version for every plugin, the catalog's (ADR-0003), and that version satisfies every plugin's declared range; a deployment installs the plugins whose range admits its console. The console's next line moves the catalog, rebuilds every plugin and moves every range, a `minor` of each published plugin: that is what moving together means under this rule.
4. **No number is chosen by hand.** A new plugin is written at `0.0.0` and `private`, the adaptation of the template, which writes 0.1.0 ([guide/adding-a-plugin.md](../guide/adding-a-plugin.md)); its first changeset is a `minor`, and the change that drops `private` lets the version pull request land it on `0.1.0`, which a maintainer publishes by hand from that pull request (ADR-0002, point 2). A private plugin is never versioned.
5. **The rule is checked.** `pnpm check` fails when the lockfile resolves `@skillcdn/console` to more than one version, or to one outside the catalog's range; when a published plugin's version is not a semver, or a changeset asks a `major` of a plugin whose major is 0; and, where a manifest declares `console`, when the catalog's console is outside it (`scripts/check-versions.mjs`).

## Consequences

- A plugin's number means here what it means anywhere: this repository's plugins and a third party's follow one rule, and the reference shows it.
- Which console a plugin goes with is data the console checks, not a convention whoever installs must know; the hand-over task quotes the range.
- Moving to the console's next line is still one change that re-releases every published plugin, as ADR-0003 wanted; the numbers go on counting instead of starting over.
- Until the console reads `console`, whoever installs learns the floor from the README and the changelog, as before; the check here holds what it can, one console version and no `major`, and the range once it is declared.
- Rejected: keeping the line rule for this repository alone (two rules, and the reference is not one); a peer dependency on `@skillcdn/console` as the declaration (a deployment's install would pull the console into the plugins' directory, and the console reads nothing of it); an `engines` key of our own in `package.json` (read by no tool, and a second place beside the manifest).
